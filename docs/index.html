The Great AI Build-Off

We made teams of AI coding agents build the same three apps, over and over — 31 times — then graded every attempt like an exam and kept the receipts. Here's how it worked and what it taught us.

1The setup: a manager and a builder

An AI coding agent is an AI that doesn't just chat — it writes files, runs commands, and tests its own code, like a very fast intern with a laptop. In our experiment, every attempt (we call each one a run) used a two-role team, like a tiny construction company:

👷‍♀️

The manager

Reads the assignment, hires a builder, checks the finished work, and files a report. One strict rule: the manager never touches the code. Not even to fix an obvious bug.

🔨

The builder(s)

Gets the assignment and actually writes the app. Sometimes one builder does the whole job; sometimes the work is split into phases, with a brand-new builder for each phase who never met the previous one.

Every run got the exact same assignment, word for word. The only things we changed between runs: which AI model played the manager, which played the builder, whether the work was split into phases, and (later) which company's AI did the building. Change one thing at a time, keep everything else fixed — that's what makes it an experiment instead of a vibe check.

2The three apps: easy, medium, boss level

All three are small money-tracking websites. Each one's assignment is a written plan broken into numbered phases — build the home page, then the lists, then the forms, and so on. More phases = more features = more places where the pieces have to fit together.

1

SpendLog

"Every penny, written down."

A spending journal. One kind of record, three pages, one form, a running total. 2 phases — the warm-up.

2

ExpenseHub

"Know where it all goes."

An expense browser. Detail pages, filtering by category, and a form that must politely reject bad input. 3 phases.

3

InvoiceDesk

"Bill it. Send it. Get paid."

An invoice tracker with rules: an invoice moves draft → sent → paid, and it cannot be marked paid until payments actually cover the amount. Plus a stats page and a data API. 4 phases — the boss level.

3The hidden traps

Here's the sneaky part. Each assignment contained a few one-line requirements that look boring but hide classic programming mistakes — like a teacher who slips one tricky question into the homework to see who's really paying attention. We call them canaries. Three favorites:

🕰️ The frozen clock

"Each entry gets the current time by default." Write that code the lazy way and the time gets stamped once, when the app starts — so every entry forever shows the same moment. The app looks fine in a demo and is quietly wrong in real life.

🚦 The route pile-up

Web pages are matched in order. If the page /expenses/new is registered after the page /expenses/{number}, the app tries to read the word "new" as a number and crashes the form. Order matters, and nothing warns you.

🌀 The weird numbers

Ask "is the amount bigger than zero?" and the bizarre value NaN (not-a-number) answers no to every comparison — so it slides right past the check. Someone could log a NaN expense and scramble your totals.

4Grading it fairly (this is the important part)

If you let an AI grade its own homework, it gives itself an A. So we built the grading to be as tamper-proof as a real exam:

  • A sealed answer key. For each app we wrote a secret test suite — 16, 25, and 32 automated checks — that the builders never see. Their folder is scrubbed before the run starts. You can't teach to a test you've never seen.
  • Blind grading. After the runs, a separate grader scores anonymized, shuffled copies of the code — it can't tell which team produced which project, so there's no favoritism.
  • Receipts for everything. Every run's cost is computed from the actual usage logs, and every prompt, finding, and test result is saved to a results file. No "trust me."
  • Repeats. One good run can be luck. The important results were run twice (or more) before we believed them.

5The five big findings

Finding 1

The cheap manager did just as well 💸

We swapped the expensive manager model for the cheapest one — and quality didn't drop at all. The best team overall was the cheapest manager + the strongest single builder: perfect scores at every difficulty level, at about half the cost of the fancy-manager version.

So what? Spend your budget where the actual work happens. Management is real work, but it doesn't need the most expensive brain in the building.

Finding 2

Relay teams drop the baton 🏃

On the hardest app, teams that split the build across phases — a fresh builder per phase, like a relay race — broke the app 3 times out of 3, with the exact same bug: builder #2 set up the pages one way, builder #3 bolted a new page on after, and the route pile-up trap sprang. Each builder's own work was fine. The bug lived between them, in the handoff. A single builder who saw the whole app never made this mistake.

So what? Every handoff is a place where a bug can hide — the same reason group projects fall apart when nobody looks at the whole thing. If you must split work, someone has to own the seams.

Finding 3

If it's not written down, it doesn't happen ✍️

The weird-numbers trap caught 9 out of 10 teams while the requirement was unwritten — everyone checked "bigger than zero" and called it done. Then we added one sentence to the assignment ("reject NaN and infinity") — and the next 5 out of 5 teams, across two different AI companies, got it right.

So what? AI does what the instructions say, not what you meant. One clear sentence beat nine smart models' intuition. Writing precise instructions is a superpower — for prompting AI and for working with humans.

Finding 4

"Think harder" mode prevents the sloppy mistakes 🧠

One AI has an adjustable "reasoning effort" dial. On high, it produced the only flawless sweep of all three apps in the whole experiment. On low, it could still build everything — but it fell for the frozen-clock trap and quietly skipped some of the tests it was told to write. Extra thinking didn't add ability; it removed carelessness.

So what? Sound familiar? Rushing doesn't make you unable to do the problem — it makes you skip the step where you'd have caught your own mistake.

Finding 5

Different AIs, same blind spots 👓

We ran the same experiment with a completely different company's AI. It did great — and it made some of the same mistakes in the same places, because the assignment's shape invited them. The blind spots belonged to the task, not the brand. (And only "think harder" mode ever fixed the subtlest one.)

So what? Switching tools doesn't rescue you from an unclear assignment. Fixing the assignment does.

6Why this matters for you

You'll probably never run this exact benchmark. But you will work with AI — and with people — on things that matter. The experiment's lessons travel:

  • Say exactly what you want. The single biggest quality jump in 31 runs came from adding one precise sentence to the instructions. Vague asks get plausible-looking, quietly-wrong results.
  • Don't grade your own homework. Every builder's own tests passed — including the broken apps'. Real checking is done by someone (or something) that didn't do the work and can't be sweet-talked.
  • Watch the handoffs. Whether it's AI phases or your group project, the bugs live between people's parts. Someone has to look at the whole thing.
  • Working ≠ correct. Every broken app in this experiment ran fine and looked fine. The bugs only appeared under tests designed to probe the edges. "It runs" is the start of checking, not the end.
  • Measure, then believe. One run is a story; a repeated, blind-graded result is evidence. That mindset is the whole scientific method, wearing a programming costume.

Try it yourself (no giant budget needed)

Pick any AI coding tool and give it a small, written assignment with one hidden trap you know the answer to — like the frozen clock. Then write three tests it never sees, and grade it. Change one word of your instructions and run it again. Congratulations: you're benchmarking.

7Glossary

AI coding agent

An AI that acts, not just chats: it creates files, writes code, runs it, and reads the errors.

Run

One complete attempt: a team gets the assignment, builds the app, gets graded.

Spec

The written assignment — what to build, feature by feature. Short for "specification."

Phase

One numbered chunk of the spec's build plan. More phases = more handoffs when work is split.

Canary

A requirement planted to detect a specific classic mistake — an early-warning tripwire.

Held-out tests

The secret exam. Automated checks the builders never see, so they can't teach to the test.

Blind grading

Scoring shuffled, anonymized work so the grader can't play favorites.

NaN

"Not a Number" — a special float value that answers no to every comparison, letting it sneak past naive checks.

Token

The unit AI text is measured (and billed) in — roughly three-quarters of a word.

Orchestrator

The manager role: delegates, verifies, reports — never implements. (The fancy word for it.)
