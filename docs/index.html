The Great AI Build-Off

I made teams of AI coding agents — Claude and Codex models in different manager/builder configurations — build the same three FastAPI apps, 48 times, then graded every attempt against tests the agents never saw — and kept the receipts. Here's how it worked and what it taught me.

1The setup: an orchestrator and an implementer

An AI coding agent is a model wired into a harness that can write files, run shell commands, and execute tests — Anthropic's Claude Code and OpenAI's Codex CLI are the two harnesses in this experiment. Every run used a two-role team:

🧭

The main agent (orchestrator)

Reads the spec, spawns the sub-agent as a separate CLI process (claude -p or codex exec), reviews the finished code against the roadmap, runs verification, and writes a report. One strict rule: it never writes or fixes implementation code. How the spawn commands work, flag by flag →

🔨

The sub-agent (implementer)

Receives the spec and builds the app. Sometimes one sub-agent implements everything (single); sometimes each roadmap phase gets a fresh sub-agent with no memory of the previous one (per-phase). What single vs. per-phase means at the process level →

Every run got the exact same prompts, verbatim — they're version-controlled files, filled mechanically. Only four things ever varied between runs: which model orchestrates (Sonnet 5, Opus 5, or Haiku 4.5); which model implements; whether one sub-agent builds everything or each phase gets its own (single vs. per-phase); and, in some runs, swapping the implementer for OpenAI's Codex (gpt-5.6-sol) — whose model_reasoning_effort dial I also tested at low, medium, and high. Change one thing at a time, hold everything else fixed.

2The three apps: easy, medium, boss level

All three are small money-tracking web apps on an identical stack — Python, FastAPI, Jinja2 templates, Bootstrap 5, in-memory storage, no database. Each spec is three files: a mission, a tech stack, and a roadmap that breaks the build into numbered phases with a literal test list per phase. More phases = more features = more places where the pieces must integrate.

1

"Every penny, written down."

A spending journal. One dataclass, three routes, one form, a running total. 2 phases — the warm-up. See it running →

4The hidden traps

I hid a few trick requirements in each spec — lines that look routine but go wrong if you code them on autopilot. I call them canaries. Whether an agent dodges them shows whether it actually read the spec. Three favorites:

🕰️ The frozen clock

"created_at defaults to the current time." Write datetime.now() as a plain dataclass default and it's evaluated once, at import — every record forever shows app-start time.

The correct form is field(default_factory=...), which runs per instance. The app demos fine and is quietly wrong in production.

🚦 The route pile-up

FastAPI matches routes in registration order. Register /expenses/{id} (an int path param) before /expenses/new, and requests for the form page try to parse "new" as an integer — instant 422.

Nothing warns you; only a request to that exact URL exposes it.

🌀 The weird numbers

Python's float() happily parses "nan" and "inf" — and every comparison with NaN is False, so nan <= 0 fails to reject it. A NaN amount sails past "must be > 0" and poisons every total.

The fix is one call: math.isfinite().

5Grading it fairly (this is the important part)

If you let an agent grade its own homework, it gives itself an A. So grading works like an exam with a sealed answer key:

  • Secret tests. Each app has a hidden test suite — 16, 25, and 32 checks — that the builders never see; it's removed from their workspace before the run starts. Passing it is the official score, because you can't study for a test you've never seen.
  • Anonymous grading. A separate grader scores shuffled, unlabeled copies of the code, re-running every check itself. It can't tell which team built which app, so it can't play favorites.
  • Receipts for everything. Every run's cost comes from its actual usage logs, and every prompt, finding, and test result is saved in the repo. No "trust me."
  • Run it twice. One good run might just be luck. Before trusting any result that mattered, I ran the same configuration again and checked that it held up.

6The five big findings

Finding 1

The cheap orchestrator lost nothing 💸

I swapped the Sonnet 5 manager for Haiku 4.5 — a model about a third the price — and quality didn't drop at all. In fact, the best setup in all 48 runs paired the cheapest manager with the strongest builder: Haiku 4.5 managing a single Opus 5. It earned a clean scorecard in every draw, on every app, at $1.20–$2.44 per build — a third to nearly half cheaper than the same builder under Sonnet 5.

So what? Quality followed the builder, not the manager. Spend your budget where the actual work happens.

Finding 2

Relay teams drop the baton 🏃

On InvoiceDesk, relay teams of Sonnet 5 (a fresh builder per phase) shipped the same broken page in every draw — five out of five, across both seasons. Builder 2 registered /invoices/{id}; builder 3 added /invoices/new after it; the route pile-up sprang. Each builder's own work looked fine, its own tests passed, and the manager's code review missed it every time. Only the secret tests caught it.

Control runs completed the picture. A single Sonnet 5 building alone ordered the routes correctly, and a relay of Opus 5 builders ran flawlessly — it read the existing routes before adding its page. So the trap needs both the relay and a mid-tier builder. And pairing the smartest manager (Opus 5) with the cheapest builder didn't help either: its review spotted the bug precisely, but a reviewer who isn't allowed to fix anything can only watch — $4.16 for a broken app.

So what? Every handoff between workers is a gap where bugs hide. Splitting work always costs something: either someone strong checks how the pieces fit together, or nobody does — and that gap is exactly where this app broke, every single time.

Finding 3

If it's not written down, it doesn't happen ✍️

While the NaN rule was unwritten, 9 of 10 builds checked amount > 0 and stopped there — every model, every team shape. Then I added one sentence to the spec ("reject NaN and infinity; check with math.isfinite") plus a matching test. All 22 runs since — Claude and Codex alike — wrote the guard.

So what? Models build what the spec says, not what you meant. One precise sentence beat nine strong models' intuition. Writing the spec well is the highest-leverage work.

Finding 4

Reasoning effort removes carelessness, not inability 🧠

Codex has a dial for how hard the model thinks before acting. On high, it produced Season 1's only flawless sweep of all three apps. On low, it could still build everything — but it fell for the frozen-clock trap and quietly dropped two required tests. (A later low-effort draw came out clean, so the dial shifts your odds; it doesn't guarantee the outcome.) Even at low effort, the explicitly written NaN rule was always honored.

So what? Extra thinking doesn't add ability — it removes the skipped-double-check mistakes. Written instructions survive even a rushed worker; unwritten expectations don't.

Finding 5

Different vendors, same blind spots 👓

Running the whole ladder with OpenAI's Codex as the builder under a Claude manager worked flawlessly — and Codex made some of the same mistakes in the same places (unencoded links, the frozen clock at low effort), because the spec's shape invited them. The blind spots belonged to the task, not the brand.

So what? Switching models doesn't rescue an unclear spec. Fixing the spec does.

7Why it matters for you

You may never run this exact benchmark, but you will build things with AI agents — and with people. The lessons carry over:

  • Say exactly what you want. The biggest quality jump in 48 runs came from adding one sentence to the spec. Vague asks get plausible-looking, quietly wrong code.
  • Don't grade your own homework. Every broken app passed its builder's own tests. Real checking comes from tests the author never saw and can't study for.
  • Watch the handoffs. Whether it's AI builders or your group project, bugs live between people's parts. Someone has to look at the whole thing.
  • Working ≠ correct. Every broken app here ran fine and demoed fine. The bugs only showed up under tests built to poke the edges.
  • Measure, then believe. One run is a story. A repeated, anonymously graded result is evidence.

Try it yourself

Take any coding agent — Claude Code, Codex — and give it a small written spec with one trap you know the answer to, like the frozen clock. Write three tests it never sees. Run it, grade it, change one sentence of the spec, and run it again. That's benchmarking.
