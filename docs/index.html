The Great AI Build-Off

We made teams of AI coding agents — Claude and Codex models in different manager/builder configurations — build the same three FastAPI apps, 31 times, then graded every attempt against held-out test suites and kept the receipts. Here's how it worked and what it taught us.

1The setup: an orchestrator and an implementer

An AI coding agent is a model wired into a harness that can write files, run shell commands, and execute tests — Anthropic's Claude Code and OpenAI's Codex CLI are the two harnesses in this experiment. Every run used a two-role team:

🧭

The main agent (orchestrator)

Reads the spec, spawns the sub-agent as a separate CLI process (claude -p or codex exec), reviews the finished code against the roadmap, runs verification, and writes a report. One strict rule: it never writes or fixes implementation code.

🔨

The sub-agent (implementer)

Receives the spec and builds the app. Sometimes one sub-agent implements everything (single); sometimes each roadmap phase gets a fresh sub-agent with no memory of the previous one (per-phase).

Every run got the exact same prompts, verbatim — they're version-controlled files, filled mechanically. The variables were: which model orchestrates (Sonnet 5, Opus 5, or Haiku 4.5), which model implements, single vs. per-phase spawning, and — in the cross-provider rounds — Codex CLI (running gpt-5.6-sol) as the implementer with its model_reasoning_effort dial swept low/medium/high. Change one axis at a time, hold everything else fixed: that's what makes it a benchmark instead of a vibe check.

2The three apps: easy, medium, boss level

All three are small money-tracking web apps on an identical stack — Python, FastAPI, Jinja2 templates, Bootstrap 5, in-memory storage, no database. Each spec is three files: a mission, a tech stack, and a roadmap that breaks the build into numbered phases with a literal test list per phase. More phases = more features = more places where the pieces must integrate.

1

SpendLog

"Every penny, written down."

A spending journal. One dataclass, three routes, one form, a running total. 2 phases — the warm-up.

2

ExpenseHub

"Know where it all goes."

An expense browser. Detail pages with 404s, category filtering with recomputed totals, and a form that must return 422 with preserved input on bad data. 3 phases.

3

InvoiceDesk

"Bill it. Send it. Get paid."

An invoice tracker with a state machine: draft → sent → paid, where sent → paid is gated on payments actually covering the invoice amount. Two related entities, billing stats, and a JSON API. 4 phases — the boss level.

3The hidden traps

Each roadmap plants a few one-line requirements that look boring but hide classic bugs — tripwires (we call them canaries) that separate reading the spec from pattern-matching it. Three favorites:

🕰️ The frozen clock

"created_at defaults to the current time." Write datetime.now() as a plain dataclass default and it's evaluated once, at import — every record forever shows app-start time.

The correct form is field(default_factory=...), which runs per instance. The app demos fine and is quietly wrong in production.

🚦 The route pile-up

FastAPI matches routes in registration order. Register /expenses/{id} (an int path param) before /expenses/new, and requests for the form page try to parse "new" as an integer — instant 422.

Nothing warns you; only a request to that exact URL exposes it.

🌀 The weird numbers

Python's float() happily parses "nan" and "inf" — and every comparison with NaN is False, so nan <= 0 fails to reject it. A NaN amount sails past "must be > 0" and poisons every total.

The fix is one call: math.isfinite().

4Grading it fairly (this is the important part)

If you let an agent grade its own homework, it gives itself an A. So the grading is built like an exam with a sealed answer key:

  • Held-out acceptance suites. Each app has a secret pytest suite — 16, 25, and 32 tests — that implementers never see: the suites are stripped from every working copy before the run starts. Agent-written tests aren't comparable across runs; the held-out suite is the primary score.
  • Blind grading. A separate grader scores anonymized, shuffled copies of each implementation against a fixed rubric, re-running every scripted check itself. It can't tell which configuration produced which tree.
  • Receipts for everything. Costs are computed from the actual session transcripts at published per-token rates; every prompt, review finding, and test result is committed to a results file in git.
  • Replicates. One good run is luck. Decision-relevant results were re-run before we ranked anything on them.

5The five big findings

Finding 1

The cheap orchestrator lost nothing 💸

Swapping the Sonnet 5 orchestrator for Haiku 4.5 — a model about a third the price — changed quality not at all. The best configuration in all 31 runs was Haiku 4.5 orchestrating a single Opus 5 implementer: blind-graded clean at every tier, twice ($1.21–$2.44 per app), 26–45% cheaper than the same implementer under Sonnet 5.

So what? Quality tracked the implementer, not the orchestrator. Spend your token budget where the actual work happens.

Finding 2

Relay teams drop the baton 🏃

On InvoiceDesk, per-phase teams (Sonnet 5 ×4, a fresh implementer per phase) shipped a broken app 3 times out of 3, under two different orchestrator models — always the same bug. The phase-2 agent registered /invoices/{id}; the phase-3 agent appended /invoices/new after it; the route pile-up sprang. Each agent's own work was fine, its own tests passed, and the orchestrator's code review missed it every time — the bug lived in the handoff, and only the held-out suite caught it. A single implementer who saw the whole app never once made this mistake.

So what? Every handoff is an integration seam where bugs hide. If you must split work, someone has to own the whole.

Finding 3

If it's not written down, it doesn't happen ✍️

While the NaN requirement was unwritten, 9 of 10 implementations — Sonnet, Opus, Haiku, every spawn strategy — validated amount > 0 and stopped there. Then we added one sentence to the spec ("reject non-finite amounts; check with math.isfinite") plus a matching test. The next 5 of 5 runs — Opus 5 and Codex both — wrote the guard and tested it.

So what? Models implement the spec's letter, not your intent. One precise sentence outperformed nine strong models' intuition. Spec-writing is the leverage point.

Finding 4

Reasoning effort removes carelessness, not inability 🧠

Codex CLI exposes a model_reasoning_effort dial. On high, gpt-5.6-sol produced the experiment's only zero-defect sweep of all three tiers — it even URL-encoded user text in links, which no other run in 31 had done. On low, it still built everything — but shipped the frozen-clock bug at tier 2 and silently compressed its tier-3 test suite, dropping two assertions the roadmap required. Notably, even low effort honored the explicit math.isfinite bullet.

So what? Extra thinking didn't add capability — it removed the skipped-the-double-check class of error. Explicit instructions survive effort reduction; unwritten expectations don't.

Finding 5

Different vendors, same blind spots 👓

Running the whole ladder with OpenAI's Codex as the implementer under a Claude orchestrator worked flawlessly — and Codex made some of the same mistakes in the same places (unencoded category links, the frozen clock at low effort), because the spec's shape invited them. The blind spots belonged to the task, not the vendor.

So what? Switching models doesn't rescue an ambiguous spec. Fixing the spec does.

6Why it matters for you

You may never run this exact benchmark, but you will build things with AI agents — and with people. The lessons transfer:

  • Say exactly what you want. The single biggest quality jump in 31 runs came from adding one precise sentence to the spec. Vague prompts get plausible-looking, quietly-wrong code.
  • Don't grade your own homework. Every implementer's own tests passed — including the broken apps'. Real verification is done by tests the author never saw and can't overfit to.
  • Watch the handoffs. Whether it's per-phase sub-agents or your group project, the bugs live between the parts. Someone has to look at the whole.
  • Working ≠ correct. Every broken app here ran fine, demoed fine, and passed its own tests. The defects only surfaced under tests designed to probe the edges.
  • Measure, then believe. One run is an anecdote; a replicated, blind-graded result is evidence. n=1 rankings are how you fool yourself.

Try it yourself

Take any agent harness — Claude Code, Codex CLI — and give it a small written spec with one trap you know the answer to, like the frozen clock. Write three pytest checks it never sees. Run it, grade it, change one sentence of the spec, and run it again. Congratulations: you're benchmarking.

7Glossary

Agent harness

The scaffolding that lets a model act: file edits, shell, tests, the loop. Claude Code and Codex CLI are harnesses; Sonnet 5 and gpt-5.6-sol are models running inside them.

Run

One complete attempt: a configuration gets the spec, builds the app, gets graded.

Spec

The written assignment — mission, tech stack, and a phase-by-phase roadmap with a literal test list.

Orchestrator / main agent

Spawns and reviews; never implements. The experiment's manager role.

Sub-agent

The implementer, spawned as a separate CLI process (claude -p / codex exec).

Canary

A requirement planted to detect one specific classic bug — an early-warning tripwire.

Held-out tests

The sealed answer key: pytest suites the implementers never see, stripped from their working copy.

Blind grading

Scoring shuffled, anonymized code against a fixed rubric, so the grader can't favor a configuration.

NaN

"Not a Number" — an IEEE-754 float for which every comparison is False, letting it slip past naive validation.

Token

The unit models read, write, and bill in — roughly three-quarters of an English word.

Reasoning effort

A dial (low/medium/high) for how much hidden thinking a model does before answering. Codex CLI exposes it per run.

Replicate

A repeat run of the same cell. The antidote to being fooled by one lucky draw.
