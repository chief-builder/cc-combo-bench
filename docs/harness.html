Under the hood

The two mechanical details everything else rests on: how an orchestrator actually spawns an implementer, and what "single" vs "per-phase" really means at the process level.

Spawning a sub-agent: claude -p and codex exec

A sub-agent isn't a function call — it's a separate operating-system process running a full agent harness in headless mode. The orchestrator writes the implementer's prompt to a temp file, then runs one of these commands from inside the run's working copy:

Claude implementers (Claude Code, headless)

cd <worktree> && claude -p \
    --model sonnet|haiku|opus \
    --permission-mode acceptEdits \
    --allowedTools "Bash" \
    --output-format text  < prompt.txt
FlagWhat it does
-p"Print" mode: non-interactive. The agent reads one prompt from stdin, works until done, prints its final report, and exits. No human in the loop.
--modelWhich Claude model implements — this is the experiment's executor axis (sonnet / haiku / opus).
--permission-mode acceptEditsFile creations and edits are auto-approved. Without this, a headless agent would stall waiting for a person to click "allow".
--allowedTools "Bash"Grants shell access so the implementer can run its own tests. An early pilot without this produced code the agent could never execute — it shipped blind.
--output-format textPlain-text final report on stdout, which the orchestrator captures as the sub-agent's handoff message.

Codex implementers (Codex CLI, headless)

cd <worktree> && codex exec --full-auto \
    --skip-git-repo-check \
    -c 'model_reasoning_effort="low|medium|high"' \
    -  < prompt.txt
FlagWhat it does
execCodex's non-interactive mode — the counterpart of claude -p.
--full-autoAuto-approves actions inside a workspace-write sandbox (the worktree plus temp dirs) — no permission prompts, no writes outside the sandbox.
--skip-git-repo-checkRuns even though the worktree isn't a normal repo root.
-c model_reasoning_effortThe "think harder" dial — the axis swept low/medium/high in the effort experiment.
-Read the prompt from stdin, same convention as the Claude spawn.

Hard-won spawn rules (each one exists because a run failed without it): the prompt file is created with mktemp so parallel runs can't collide on a shared path; the spawn runs in the foreground with a 10-minute timeout, because backgrounding it orphaned sub-agents in early runs; and each sub-agent is started exactly once — a duplicate spawn would double-implement and corrupt the run's cost accounting.

Costs are measured from these processes' session transcripts afterward — every token each spawn read and wrote, priced at published rates. That's why a worktree path is never reused: its transcript folder is the run's receipt.

Single vs. per-phase: one builder or a relay

Both strategies deliver the same roadmap. The difference is how many sub-agent processes it takes and what each one knows.

Single

One spawn implements every phase in one sitting. Its prompt is the whole assignment; it designs the app end-to-end, sees the entire route table, and its tests grow alongside the code. One process, one context, one coherent mental model.

Per-phase (the relay)

One spawn per roadmap phase, in order — four separate processes for InvoiceDesk. Each is a brand-new agent with zero memory of its predecessors: a fresh process has a fresh context window. The only things that carry forward are the files on disk and the sub-agent's final report, which the orchestrator does not relay onward.

Mechanically, a per-phase run works like this: phase 1's sub-agent gets a "you're starting from scratch, build phase 1" prompt. Every later phase N gets a different prompt: "phases 1 through N−1 are already built by someone else — read the existing code first, then implement phase N on top of it, without breaking what's there." Between spawns, the orchestrator reviews the new phase's code (it may record defects, but it may not fix them or warn the next sub-agent — that would contaminate the axis being measured).

Why test this at all? Because the relay models how real teams — human and AI — actually ship: nobody holds the whole system in their head, and work arrives in increments built on other people's code. The campaign's sharpest results live exactly here: the relay's phase boundaries created an integration seam where a route-registration bug appeared 3 times out of 3 with Sonnet implementers, was invisible to every in-run review, and never happened when one agent saw the whole app — yet a relay of Opus implementers read the inherited code carefully enough to avoid it. Same roadmap, same prompts, different number of minds.

Both strategies use fixed, version-controlled prompt files, filled mechanically per run — the wording is never improvised, so the strategy itself is the only thing that varies between a "single" run and a "per-phase" run of the same models.
